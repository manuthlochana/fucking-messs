## 1. The 100-Point Forensic Possibilities & Edge-Case Matrix

Format: `[ID] - [Edge Case / Tactic] -> [Detection Algorithm / Mitigation]`

### Category A — Data Ingestion, Anti-Bot & Selector Edge Cases (20)

1. Site swaps price into an `<img>` sprite (price-as-image) to defeat text scraping -> Run OCR fallback only on domains flagged `text_extraction_failed_3x`; don't OCR by default (too expensive on 4GB box).
2. Cloudflare "I'm Under Attack Mode" full-page JS challenge with 5s delay -> Detect via response containing `jschl_vc`/`cf-please-wait` markers; queue domain into a slow-lane profile with real browser + 6-8s dwell time instead of retrying fast.
3. Price rendered via WebSocket push after initial load (real-time "flash sale" price sync) -> Attach a `page.on('websocket')` listener rather than polling DOM; extract from the socket payload directly.
4. Shadow DOM-encapsulated price components (common in modern component libraries) -> Use `page.evaluateHandle` with explicit `shadowRoot` traversal; standard `querySelector` silently returns null.
5. Server-side randomized CSS class hashes per request (`.a3f9x1`) defeating static selectors -> Select by stable structural anchors (data-testid, aria-label, or nth-child position relative to a stable parent) instead of class names.
6. Infinite-scroll product listing pages that never expose a "next page" URL -> Simulate scroll-to-bottom with mutation-observer-based termination (stop when no new nodes appear for 2 consecutive scrolls), cap at a max scroll count to bound worst-case time.
7. Decoy/mirror domains serving intentionally wrong data to scrapers identified by IP reputation -> Cross-check scraped price against a second independent proxy exit node periodically; large divergence flags the domain for manual trust review.
8. robots.txt disallow rules covering the exact paths you need -> Maintain a documented compliance policy per jurisdiction/ToS; for disallowed paths, prefer the site's own public API/sitemap/RSS feed if one exists rather than scraping the disallowed HTML.
9. Sitemap.xml listing stale/deleted product URLs -> Treat sitemap as a discovery hint only, never a truth source; a 404/redirect response during actual fetch auto-demotes the URL from the crawl queue.
10. Session-bound pricing (price differs per logged-in "loyalty tier" cookie) -> Always scrape from a clean, unauthenticated session; log-in-gated pricing is out of scope for baseline comparison and should be labeled separately if surfaced at all.
11. Double-encoded/garbled UTF-8 in Sinhala product titles -> Force explicit `charset` detection via response headers + BOM sniffing before decode; never assume UTF-8 blindly on older SL retail CMS platforms.
12. Anti-scraping "trap" pages returning plausible-but-fake catalog data only to flagged bot IPs -> Validate scraped catalog size against a rough expected order-of-magnitude (a "50,000 products" trap page from a small retailer is a red flag); anomalous catalog size triggers a manual spot-check.
13. AJAX pagination using non-standard query params that silently reset to page 1 -> Track the actual product IDs returned per "page" request; if page N and page N+1 return overlapping ID sets, treat pagination as broken and fall back to a fixed max-depth crawl.
14. Content-Security-Policy blocking inline script execution needed for `page.evaluate` injection -> Use `addInitScript` (injected before page scripts run) rather than post-load `evaluate` calls, which CSP is more likely to permit.
15. Rate-limiting keyed on TLS JA3 fingerprint rather than IP -> Rotate the underlying HTTP client/TLS stack (not just proxy IP) for domains that continue blocking despite fresh IPs; use a stealth-patched Chromium rather than a bare `httpx` client for these.
16. Product page returning HTTP 200 with a "this item has been discontinued" banner instead of 404 -> Maintain a per-domain regex list of discontinuation banner phrases; on match, soft-archive the listing rather than treating 200 as "still valid."
17. Currency toggle widget defaulting to USD for foreign-looking user agents, masking true LKR price -> Force `Accept-Language: si-LK,en-LK` and a Sri Lankan timezone/locale in the browser context to avoid being auto-switched to a foreign price view.
18. Lazy-loaded reviews section requiring scroll-triggered XHR that your headless scrape never fires -> Explicitly dispatch a synthetic scroll event and await the specific XHR route pattern (`**/reviews*`) via `page.waitForResponse` before extracting.
19. Anti-bot fingerprinting via mouse-movement/timing entropy absence -> For high-value targets only (cost-benefit), add randomized bezier-curve mouse movement and variable dwell time via a stealth plugin rather than instant programmatic clicks.
20. Duplicate product listings across a merchant's multiple sub-domains (mobile.site.lk vs www.site.lk) inflating apparent competition -> Canonicalize by merchant business entity (not domain string) using a manually-curated domain-to-merchant mapping table.

### Category B — Canonical Normalization & Variant Collision Traps (20)

21. Same physical product sold under different brand-assigned regional names (e.g., a "Galaxy A-series" rebrand in one market) -> Maintain a cross-region model-name alias table sourced from brand global newsroom pages, keyed to a shared MPN where available.
22. Two genuinely different products sharing a marketing name across generations (e.g., a laptop line name reused with a totally different chassis 3 years later) -> Never key canonical identity on marketing name alone; require year/generation + model-number co-match.
23. Bundled SIM/data-plan pricing folded into device price by telco-partnered listings -> Detect telco-bundle keywords ("with postpaid plan", "on contract") and exclude from device-only price comparison, tag as a separate "carrier bundle" listing type.
24. Color variant treated as a separate canonical product by a merchant's own CMS export feed -> Normalize at ingestion time using the color-alias table (from base blueprint §A2.18) before the spec-fingerprint hash is computed, so color never enters the hash input.
25. Regional voltage/plug variants of small appliances silently listed as identical to the local-market version -> Require explicit voltage/frequency (110V/60Hz vs 230V/50Hz) extraction for the appliance category; mismatched-voltage imports get a mandatory compatibility-risk flag, never silently merged with the region-correct SKU.
26. "Global Version" vs "Chinese Version" firmware distinctions for cross-border imports (missing Google Play Services, different app stores) -> Treat firmware-region as a first-class canonicalization attribute for any brand/category known to ship region-locked firmware.
27. Refurbished units re-sold under the original manufacturer part number with no condition flag in the feed -> Cross-reference seller category/tag metadata (not just title text) — many refurb marketplaces expose condition in a structured field your title-regex misses.
28. Capacity mislabeling from binary vs decimal GB confusion in scraped specs (rare but occurs in cheaper accessory listings) -> Sanity-bound extracted capacity values against known valid SKU capacities for that product family; out-of-range values get flagged for manual correction rather than silently stored.
29. Sub-brand/OEM white-label collision (identical hardware sold under two different consumer-facing brand names) -> Where teardown/FCC-ID evidence indicates identical internals, link the two canonical entries via a `same_hardware_as` relation without merging their separate warranty/brand-support realities.
30. Merchant feed re-uses a single generic image/title template across multiple actual SKUs (bulk CSV upload error) -> Cross-validate scraped price against the expected price range for the claimed canonical product; extreme outliers (a "$50 flagship phone") trigger a mismatch-review flag rather than auto-publishing.
31. Trailing/leading whitespace and invisible unicode characters in titles defeating exact-match dedup -> Normalize via Unicode NFKC + trim + collapse-whitespace as a mandatory first step before any comparison (fuzzy or exact).
32. Storage tier naming inconsistency ("128GB" vs "128 GB" vs "128gb" vs "0.128TB") -> Parse to a canonical integer-MB representation immediately at ingestion; never compare raw strings across sources.
33. Bundle-vs-standalone SKU confusion for peripherals (e.g., "console + controller" listed under the same title as "console only") -> Require explicit accessory-inclusion parsing; treat bundle SKUs as distinct canonical entries linked via a `bundle_of` relation, not variants of the base product.
34. Bootleg/counterfeit listings using an exact legitimate title+images but implausible price (>40% below any verified floor) -> Auto-flag for a "verify authenticity" risk tag rather than either blocking or trusting; extreme sub-floor pricing is the single strongest counterfeit signal in this dataset.
35. Multi-pack listings (e.g., "3-pack of X") title-matching the singular product -> Extract explicit quantity multipliers from title text and normalize to per-unit price before any cross-merchant comparison.
36. Developer/engineering-sample units illegally resold (visible via distinct "ES" markings in serial/model text) -> Treat as a legally and functionally distinct product; these have no consumer warranty path and must never canonicalize against the retail SKU.
37. Same canonical product, but one listing is the "unlocked" and another is "carrier variant" sharing an identical title string -> Extract carrier-lock status from description body text (not just title) via keyword/LLM classification pass; missing data defaults to "unknown," never "unlocked."
38. Import listings quoting spec sheets from the wrong regional variant (e.g., US spec battery capacity shown for an EU unit with a different battery) -> Cross-check extracted specs against the official regional spec PDF (Phase 1 ground truth) matched by the declared import-origin market, not the default/global spec page.
39. Near-duplicate canonical entries created because spec-fingerprint hashing was sensitive to attribute ordering -> Sort all attribute keys alphabetically and normalize value formatting before hashing so semantically identical spec sets always produce an identical fingerprint.
40. LLM-based entity resolution hallucinating a plausible-sounding model number when the source text is genuinely ambiguous -> Require the LLM to output a structured confidence score alongside any inferred field; anything below a set threshold routes to the human/secondary-source verification queue instead of being written as fact.

### Category C — Merchant Deception, Warranty Traps & Payment Surcharges (20)

41. "Official Warranty" badge displayed as a static site-wide image regardless of actual per-product agent status -> Never trust a site-level badge; warranty classification must be verified per canonical-product-per-merchant pair against the authorized-agent allowlist.
42. Warranty card issued at point of sale naming a different legal entity than the selling website -> Where a physical-store visit or invoice sample is available, cross-check the registered business name against the company registry lookup; mismatch is a hard downgrade to "unenforceable" tier.
43. "Extended warranty" upsell that is actually a third-party insurance product with exclusions unrelated to the manufacturer -> Classify extended-warranty upsells as a separate risk category entirely from base warranty tier; don't let a purchased extension mask a weak base warranty in the score.
44. Fine-print restocking fee (e.g., 15-20%) buried in a linked T&C page never surfaced on the product page itself -> Periodically crawl and diff the linked policy pages for known high-friction phrases ("restocking fee", "non-refundable once opened") and surface them as a standing merchant-level flag, not a per-listing one.
45. Store advertises a price match guarantee that excludes the exact class of competitor most likely to be cheaper (grey-market importers) -> Extract and store the actual exclusion clauses; a price-match guarantee with broad exclusions should not raise the merchant's reliability score the way an unconditional one would.
46. Bait pricing on a "starting from" model tier while the in-stock reality is only the most expensive configuration -> Verify actual in-stock configuration matches the advertised "starting from" configuration before letting that price anchor any comparison; if only the top config is available, surface that config's real price instead.
47. Fake urgency via a merchant-wide "flash sale ends tonight" banner present on every visit for months -> Track banner text hash across polling cycles; identical unchanging "urgent" banners for 60+ days get demoted from the UI as non-credible.
48. Card-fee surcharge disclosed only after selecting a specific card network (Visa vs local bank cards priced differently) -> Sample the checkout flow across the 2-3 most common local payment methods, not just a single generic "credit card" test, since surcharge structures can be network-specific.
49. Mintpay/Koko approval requiring a hard credit check not disclosed until deep into checkout, creating sunk-cost pressure -> Where legally/technically feasible, surface the BNPL provider's own disclosed terms (APR, hard-pull policy) alongside the merchant listing rather than only the merchant's marketing copy.
50. "No Cost EMI" installment plans that embed the interest cost into an inflated base price versus the cash price -> Compare cash price against the total sum of the advertised "0% EMI" installments; any positive delta is the true hidden interest cost and must be surfaced explicitly, not accepted as genuinely zero-cost.
51. Warranty period stated in the title (e.g., "1 Year Warranty") contradicted by shorter terms in the actual printed/PDF warranty card -> Weight the formal warranty document (when obtainable) over marketing title text in all cases; title text is a claim, the card is the record.
52. Merchant swaps to a newly-registered look-alike domain after accumulating negative reviews on the old one -> Track WHOIS registration age and any historical domain-name lineage/redirect patterns; a pattern of serial domain-hopping after review pile-ups is a severe reliability red flag, not a fresh start.
53. Physical store address listed on-site is a shared virtual-office/mailbox service address, not a real retail location -> Cross-check listed addresses against known virtual-office provider address lists for Colombo/Kandy commercial buildings; flag mismatches for the merchant-legitimacy score.
54. "Authorized Reseller" claims for a brand that does not operate a formal authorized-reseller program in Sri Lanka at all -> Maintain the allowlist as an explicit *closed* list (brands with zero disclosed SL partners get every "authorized" claim auto-flagged as unverifiable, since there is no possible ground truth to confirm against).
55. Delivery-time bait ("same day delivery available") that in practice is only honored within an undisclosed narrow geographic radius -> Sample delivery-estimate API responses (where exposed) across multiple simulated delivery postcodes/districts, not just the merchant's home city.
56. Currency-devaluation price hikes applied same-day, but LKR-strengthening price cuts delayed by weeks or never applied -> Compute a rolling asymmetry index per merchant: average lag (in days) between a CB rate movement and the merchant's corresponding price adjustment, separated by direction of the FX move.
57. "Grey import, no warranty" disclosed only in small text at the very bottom of a long description -> NLP-scan the full description body (not just the first paragraph, which many extraction pipelines default to) for warranty-disclaiming phrases before defaulting warranty_tier to anything better than "unstated."
58. Fake "verified purchase" badges on on-site reviews that are not actually tied to a real transaction system -> Where the platform doesn't expose a genuine verified-purchase API, treat all on-site (non-third-party) reviews as unverified by default in the sentiment layer, regardless of any badge shown.
59. Merchant selectively deletes negative reviews from their own site while leaving them live on third-party platforms (Google Business, Facebook) -> Cross-reference on-site review volume/sentiment against independent third-party review platforms for the same merchant; a large sentiment gap is itself a data point worth surfacing.
60. Trade-in offers advertised at an attractive headline value, actually contingent on undisclosed condition-grading that reduces payout post-submission -> Treat advertised trade-in values as unverified/aspirational in the UI unless you have a corroborating sample of an actual completed trade-in payout.

### Category D — Real-World Defect, Teardown & Astroturf Mining Edge Cases (20)

61. iFixit repairability score conflated with reliability (a hard-to-repair product isn't necessarily failure-prone) -> Store repairability score and failure-rate signal as two separate dossier fields; never let a low repairability score silently lower a "known defects" severity display.
62. Component-level teardown reveals a cost-cut part (e.g., cheaper display driver IC) mid-generation without a model-number change ("silent revision") -> Where teardown video/forum evidence identifies a silent internal revision, track it as a `component_teardowns` row keyed by observed serial-number range or manufacture-date range, distinct from the nominal model.
63. Battery degradation curves reported inconsistently across sources (some cycle-count based, some calendar-time based) -> Normalize all battery-health mentions into both a cycle-count and calendar-month axis where the source specifies enough detail to do so; discard imprecise mentions rather than force-fitting them to one axis.
64. A widely-cited "bendgate"-style structural failure claim that traces back to a single viral video rather than broad corroboration -> Require the ≥2-independent-source corroboration gate (base blueprint §A4.45) before any structural defect claim is elevated above "isolated report" severity, regardless of the original video's view count.
65. Hardware issue real but only manifests under an extreme edge-case workload (e.g., sustained 4K export on a thin laptop) irrelevant to 95% of buyers -> Tag defect entries with an explicit `trigger_workload` field so the AI advisor can correctly say "irrelevant to your stated everyday-use case" instead of blanket alarm.
66. YouTube algorithm-favored "one year later" reliability videos posted by the same influencer for every single flagship model regardless of actual findings (templated content) -> Weight source diversity, not just source count; ten videos from one channel should count as roughly one independent data point, not ten.
67. Regional water/humidity-related failures common in tropical climates not well represented in temperate-market forums (US/EU) -> Explicitly search Sri Lankan/South Asian/Southeast Asian tech forums and Facebook groups for climate-specific failure patterns (corrosion, humidity-related battery swelling) that Western sources systematically under-report.
68. Firmware update mid-review-cycle changes camera processing algorithm, making pre-update sample photos/complaints obsolete -> Timestamp defect/quality mentions against the firmware version in effect at the time, extracted from the source text or inferred from publish date vs. known OTA release dates.
69. Astroturf reviews using AI-generated text that passes basic bot-detection heuristics (varied sentence length, no obvious template) -> Supplement heuristic detection with a cross-check against purchase-verification signals and posting-velocity anomalies rather than relying on text-pattern detection alone, since LLM-generated fake reviews increasingly defeat pure NLP heuristics.
70. A defect thread that is actually about a counterfeit/clone unit, mistakenly attributed to the genuine product's dossier -> Cross-reference defect-report context for counterfeit-indicator language ("bought from [suspicious marketplace]", price implausibly low) before attributing a reported failure to the genuine product's reliability profile.
71. Manufacturer-acknowledged recall or extended-warranty-program for a specific defect not reflected in generic forum sentiment scraping -> Maintain a dedicated periodic check against official brand support/recall pages as a higher-authority source that should override or heavily weight above forum sentiment when present.
72. Overrepresentation of complaint threads due to complaint-threads simply being more heavily indexed/upvoted than satisfaction posts on forums by platform nature -> Apply the base-rate correction from base blueprint §A4.47 (sampled neutral/positive control set) specifically calibrated per source platform, since the bias magnitude differs between Reddit, YouTube comments, and Facebook groups.
73. Teardown video reveals adhesive-heavy construction correlating with future battery-swell risk, a predictive signal not yet reflected in current complaint volume -> Allow the forensic layer to log a `predictive_risk_signal` (from construction analysis) distinct from `confirmed_defect_rate` (from complaint mining), clearly labeled as forward-looking, not yet realized.
74. Cross-contamination between a product's defect dossier and its unrelated same-numbered accessory (e.g., "Model X earbuds case" issues bleeding into "Model X phone" dossier due to loose keyword matching) -> Require full canonical-product-ID matching (not keyword substring matching) before attributing any mined defect mention to a dossier.
75. Review-bombing driven by an unrelated corporate controversy (e.g., a brand PR scandal) rather than the product's actual quality -> Detect sentiment spikes that are temporally correlated with a known news event unrelated to the product itself; these should be excluded from the hardware-defect dossier even if included in a separate "brand controversy" note.
76. Successive firmware updates that fix one defect while introducing a new regression, both attributed loosely to "software issues" -> Track defect entries at the firmware-version granularity so a fixed-then-regressed pattern is visible as two distinct time-bounded entries, not a single ambiguous ongoing complaint.
77. Community consensus forming around a fix/workaround (e.g., "always disable X setting") that masks rather than resolves the underlying defect -> Where a workaround is mentioned, still log the underlying defect at full severity; a popular workaround should not be misread as evidence the defect is minor.
78. Sample-size collapse for niche/low-sales-volume products where only 3-4 total online mentions exist -> Explicitly label dossiers as "low confidence — limited public data" below a minimum source-count threshold, rather than presenting a thin dataset with the same confidence framing as a high-volume flagship's dossier.
79. Non-native-English review text auto-translated losing critical negation ("not bad" mistranslated as negative) -> For any source in a non-English/non-Sinhala language relevant to your markets, use a translation step specifically validated for negation-preservation, or route to a bilingual-capable LLM pass rather than a naive translation API.
80. Historical defect data persisting in the dossier after a component-supplier change resolves the issue in later production runs -> When manufacturer or credible teardown sources confirm a supplier/component change, timestamp a `resolved_as_of_batch` marker on the defect entry so later-manufactured units aren't penalized by an inherited historical score.

### Category E — System Performance, Low-Memory (4GB VPS) & Multi-LLM Rate-Limit Controls (20)

81. Redis queue growing unbounded when discovery rate outpaces the 5-minute-per-item worker throughput -> Set a max queue depth with a priority eviction policy (drop lowest-priority rediscoveries first) rather than let Redis memory usage grow until it competes with Postgres/Playwright for the same 4GB.
82. A single stuck Playwright page (JS infinite loop on a malicious/broken page) consuming its full worker slot indefinitely -> Wrap every phase in an explicit `asyncio.wait_for` timeout tied to the phase's time budget; a hung page must be hard-killed at the budget boundary, never allowed to silently consume the next item's window.
83. Token-budget overrun mid-Phase-3 LLM defect-summarization call exceeding the model's context window on unusually verbose sources -> Pre-truncate/chunk source text to a token-budgeted size *before* the API call (using a local tokenizer estimate), never let the API's own error response be your first signal of an oversized prompt.
84. Simultaneous rate-limit exhaustion across all pooled Gemini keys during a discovery burst (e.g., a new product launch triggers many parallel new-entity workers) -> Cap the number of *concurrent* forensic-pipeline workers independent of queue depth, so a discovery burst queues up rather than triggering a synchronized rate-limit wall across every key at once.
85. Fallback model (Groq/Llama) producing lower-quality structured output than the primary, causing downstream JSON-parsing failures -> Validate every LLM response against a strict schema (e.g., Pydantic) regardless of which model produced it; a fallback-model schema failure should trigger a second fallback attempt with a more constrained/simplified prompt, not a silent partial commit.
86. Long-tail low-priority background tasks (routine re-summarization) starving the CPU during a burst of new high-priority discovery items -> Use two separate queue priorities/worker pools with the low-priority pool explicitly capped at a small concurrency (e.g., 1) so it never meaningfully competes with new-item discovery for the shared 2 cores.
87. Postgres connection exhaustion when the orchestrator opens a fresh connection per phase rather than reusing one per item -> Use a single connection (or a small pooled connection) per worker item lifecycle, explicitly released back to the pool in a `finally` block, given the tight `max_connections` ceiling on this hardware.
88. Playwright browser binary itself consuming disk space across frequent version auto-updates -> Pin a specific Playwright/Chromium version in the deployment and update deliberately on a schedule, rather than letting automatic updates silently increase both disk footprint and memory-per-instance over time.
89. Currency/exchange-rate API itself rate-limiting or going down, silently freezing Phase 2 arbitrage math on a stale rate -> Cache the last-known-good FX rate with an explicit staleness timestamp; if the live fetch fails, proceed using the cached rate but flag the resulting arbitrage calculation as "FX data may be stale" rather than blocking the whole pipeline.
90. A single malformed/adversarial webpage crashing the Python process itself (e.g., a decompression bomb disguised as a small gzip response) -> Enforce hard byte-size caps on all fetched response bodies before decompression/parsing, rejecting oversized responses outright rather than trusting `Content-Length` headers.
91. Zombie Chromium processes surviving a crashed Python worker, silently consuming RAM until an OS-level reap -> Run workers under a process supervisor (e.g., `supervisord` or a systemd unit) configured to kill the entire process group (not just the parent PID) on worker restart, since Playwright spawns child processes that outlive an ungracefully-killed parent.
92. Vector embedding generation calls competing with the primary reasoning LLM calls for the same rate-limited API key pool -> Route embedding calls to a separate, cheaper/dedicated key pool (or a local lightweight embedding model) so embedding-generation volume never throttles the higher-value reasoning calls in Phase 3.
93. `pg_stat_statements` or logging overhead itself consuming meaningful CPU/memory on a 2-core box under sustained load -> Keep verbose query logging disabled in steady-state production; enable only temporarily and narrowly when actively debugging a specific slow-query hypothesis.
94. Time-budget phases (60/60/90/60/30) drifting over real wall-clock time due to network latency variance, causing the "5-minute" pipeline to silently take 8-9 minutes under load -> Track actual elapsed time per phase against budget and if a phase overruns, hard-truncate remaining sub-steps within that phase (partial data + explicit `phase_incomplete` flag) rather than letting overruns cascade indefinitely.
95. Disk fills silently from accumulated Playwright trace/video artifacts left over from ad-hoc debugging sessions -> Automate a scheduled cleanup job for any debug-artifact directories with a short (e.g., 48-hour) retention window, since manual cleanup is easy to forget on a small unattended VPS.
96. Multiple workers racing to create the same new canonical_product row simultaneously under load -> Rely on the DB-level unique constraint + `ON CONFLICT DO NOTHING`/advisory lock pattern (base blueprint §A2.27) rather than any application-level "check-then-insert," since race windows widen under real concurrency, not narrow.
97. LLM API latency spikes (provider-side, not rate-limit) silently consuming the majority of a phase's time budget with nothing to show for it -> Set an aggressive per-call timeout well below the phase budget (e.g., 15s for a call within a 60s phase) so a single slow call can retry against a fallback key/model rather than exhausting the whole phase.
98. Swap thrashing triggered specifically by the combination of a Postgres autovacuum run and a Playwright-heavy phase overlapping in time -> Stagger scheduled maintenance (vacuum, index rebuilds) into hours/windows with historically low discovery-queue volume, rather than relying purely on Postgres's own autovacuum scheduling heuristics.
99. Cost/quota tracking drifting out of sync with actual provider-side usage (free-tier dashboards often lag by hours) -> Maintain your own authoritative in-app request counter per key with conservative self-imposed limits set below the provider's documented cap, rather than trusting real-time provider dashboards as your throttling signal.
100. A full pipeline crash mid-Phase-4 leaving a canonical product partially written (spec data committed, forensic dossier missing) and indistinguishable from a fully-processed entry -> Use an explicit `pipeline_status` enum (`discovered`, `phase1_done`, ..., `complete`, `failed`) on the canonical product row, and only surface products to the user-facing app once `pipeline_status = 'complete'`.

## 2. The 5-Minute Python Async State Machine

This is a structural skeleton: it shows the timing discipline, fallback-tree pattern, and DB-commit boundaries. It intentionally omits the actual scraping/parsing logic bodies (those are source-specific and belong in separate modules) so the orchestration logic stays readable.

```python
"""
forensic_orchestrator.py

5-minute (300s) autonomous forensic pipeline for a single newly-discovered
canonical product candidate. Designed for a 2-core/4GB VPS running under
a Celery/Redis worker pool with concurrency capped externally (see
Category E rules #84, #86).
"""

import asyncio
import enum
import logging
import time
from dataclasses import dataclass, field
from typing import Any, Optional

import asyncpg

logger = logging.getLogger("forensic_pipeline")

# ---- Time budget (seconds), matching the 6-phase spec -----------------
PHASE_BUDGETS = {
    "phase1_ground_truth": 60,
    "phase2_arbitrage": 60,
    "phase3_defect_mining": 90,
    "phase4_merchant_forensics": 60,
    "phase5_peer_cohort": 30,
}
TOTAL_BUDGET = sum(PHASE_BUDGETS.values())  # 300s


class PipelineStatus(str, enum.Enum):
    DISCOVERED = "discovered"
    PHASE1_DONE = "phase1_done"
    PHASE2_DONE = "phase2_done"
    PHASE3_DONE = "phase3_done"
    PHASE4_DONE = "phase4_done"
    PHASE5_DONE = "phase5_done"
    COMPLETE = "complete"
    FAILED = "failed"
    PARTIAL = "partial"          # hit a time overrun; usable but incomplete


@dataclass
class PipelineContext:
    """Accumulates results across phases; committed incrementally so a
    crash mid-pipeline never loses fully-completed earlier phases."""
    candidate_id: str
    raw_title: str
    source_url: str
    status: PipelineStatus = PipelineStatus.DISCOVERED
    ground_truth_specs: dict = field(default_factory=dict)
    arbitrage: dict = field(default_factory=dict)
    defects: list = field(default_factory=list)
    merchant_forensics: dict = field(default_factory=dict)
    peer_cohort: dict = field(default_factory=dict)
    phase_timings: dict = field(default_factory=dict)
    errors: list = field(default_factory=list)


class LLMKeyPool:
    """Per-key rate-limit tracking with independent cooldowns.
    Implements Category E rule #84 (don't let a burst hit every key at once)
    and rule #56/#99 (self-imposed conservative limits, not provider dashboards).
    """

    def __init__(self, keys: list[dict]):
        # keys: [{"provider": "gemini", "key": "...", "rpm_limit": 15}, ...]
        self._keys = keys
        self._cooldown_until: dict[str, float] = {}
        self._request_log: dict[str, list[float]] = {k["key"]: [] for k in keys}

    def _is_available(self, key_entry: dict, now: float) -> bool:
        if self._cooldown_until.get(key_entry["key"], 0) > now:
            return False
        # Self-imposed conservative RPM check (rule #99)
        window = [t for t in self._request_log[key_entry["key"]] if now - t < 60]
        return len(window) < key_entry["rpm_limit"] * 0.8  # 80% safety margin

    def acquire(self) -> Optional[dict]:
        now = time.monotonic()
        for key_entry in self._keys:
            if self._is_available(key_entry, now):
                self._request_log[key_entry["key"]].append(now)
                return key_entry
        return None

    def mark_rate_limited(self, key_entry: dict, cooldown_s: float = 30.0):
        self._cooldown_until[key_entry["key"]] = time.monotonic() + cooldown_s
        logger.warning(f"Key {key_entry['provider']} cooling down for {cooldown_s}s")


async def call_llm_with_fallback(
    pool: LLMKeyPool,
    prompt: str,
    schema_validator,
    per_call_timeout: float = 15.0,
    max_attempts: int = 3,
) -> Optional[dict]:
    """Implements Category E rule #85 (schema-validate every response,
    fallback on failure) and rule #97 (aggressive per-call timeout)."""
    for attempt in range(max_attempts):
        key_entry = pool.acquire()
        if key_entry is None:
            logger.error("All LLM keys exhausted/cooling down; skipping this call")
            return None
        try:
            raw_response = await asyncio.wait_for(
                _dispatch_llm_call(key_entry, prompt), timeout=per_call_timeout
            )
            parsed = schema_validator(raw_response)  # raises on schema mismatch
            return parsed
        except asyncio.TimeoutError:
            logger.warning(f"LLM call timed out on attempt {attempt+1} ({key_entry['provider']})")
            continue  # try next key/attempt, don't burn remaining phase budget
        except RateLimitError:
            pool.mark_rate_limited(key_entry)
            continue
        except SchemaValidationError as e:
            logger.warning(f"Schema validation failed: {e}; retrying with simplified prompt")
            prompt = _simplify_prompt(prompt)
            continue
    return None  # exhausted attempts; caller must handle partial data


async def run_phase(
    phase_name: str,
    coro,
    ctx: PipelineContext,
) -> bool:
    """Generic phase runner enforcing the hard time budget (Category E #82, #94).
    Returns True if the phase completed within budget, False if truncated."""
    budget = PHASE_BUDGETS[phase_name]
    start = time.monotonic()
    try:
        await asyncio.wait_for(coro(ctx), timeout=budget)
        ctx.phase_timings[phase_name] = time.monotonic() - start
        return True
    except asyncio.TimeoutError:
        elapsed = time.monotonic() - start
        ctx.phase_timings[phase_name] = elapsed
        ctx.errors.append(f"{phase_name} truncated at {elapsed:.1f}s (budget {budget}s)")
        logger.warning(f"Phase {phase_name} exceeded budget; proceeding with partial data")
        return False
    except Exception as e:
        ctx.errors.append(f"{phase_name} failed: {e}")
        logger.exception(f"Phase {phase_name} raised an exception")
        return False

async def run_forensic_pipeline(
    ctx: PipelineContext,
    db_pool: asyncpg.Pool,
    llm_pool: LLMKeyPool,
) -> PipelineContext:
    pipeline_start = time.monotonic()

    phase_sequence = [
        ("phase1_ground_truth", lambda c: phase1_ground_truth(c), PipelineStatus.PHASE1_DONE),
        ("phase2_arbitrage", lambda c: phase2_arbitrage(c), PipelineStatus.PHASE2_DONE),
        ("phase3_defect_mining", lambda c: phase3_defect_mining(c, llm_pool), PipelineStatus.PHASE3_DONE),
        ("phase4_merchant_forensics", lambda c: phase4_merchant_forensics(c), PipelineStatus.PHASE4_DONE),
        ("phase5_peer_cohort", lambda c: phase5_peer_cohort(c), PipelineStatus.PHASE5_DONE),
    ]

    async with db_pool.acquire() as conn:  # single connection for the item's lifecycle (rule #87)
        for phase_name, phase_coro, done_status in phase_sequence:
            completed_in_budget = await run_phase(phase_name, phase_coro, ctx)
            ctx.status = done_status if completed_in_budget else PipelineStatus.PARTIAL

            # Incremental commit after every phase — a crash later never
            # loses earlier, fully-validated phase data (rule #100).
            await _commit_phase_result(conn, ctx, phase_name)

            total_elapsed = time.monotonic() - pipeline_start
            if total_elapsed > TOTAL_BUDGET:
                logger.warning(
                    f"Total pipeline elapsed {total_elapsed:.1f}s exceeds {TOTAL_BUDGET}s "
                    f"budget after {phase_name}; truncating remaining phases (rule #94)."
                )
                ctx.status = PipelineStatus.PARTIAL
                break

        if ctx.status != PipelineStatus.PARTIAL and not ctx.errors:
            ctx.status = PipelineStatus.COMPLETE
        elif ctx.errors and ctx.status not in (PipelineStatus.PARTIAL,):
            ctx.status = PipelineStatus.PARTIAL

        await _commit_final_status(conn, ctx)

    return ctx


async def _commit_phase_result(conn: asyncpg.Connection, ctx: PipelineContext, phase_name: str):
    """Each phase's data lands in its own table/columns immediately —
    never buffered purely in memory until pipeline end."""
    if phase_name == "phase1_ground_truth" and ctx.ground_truth_specs:
        await conn.execute(
            """
            UPDATE canonical_products
            SET attributes = attributes || $1::jsonb,
                pipeline_status = $2,
                updated_at = now()
            WHERE id = $3
            """,
            ctx.ground_truth_specs, ctx.status.value, ctx.candidate_id,
        )
    elif phase_name == "phase2_arbitrage" and ctx.arbitrage:
        await conn.execute(
            """
            INSERT INTO currency_arbitrage_logs
                (canonical_product_id, us_msrp_usd, fx_rate, landed_cost_lkr,
                 local_price_lkr, margin_pct, classification, computed_at)
            VALUES ($1, $2, $3, $4, $5, $6, $7, now())
            """,
            ctx.candidate_id,
            ctx.arbitrage.get("us_msrp_usd"),
            ctx.arbitrage.get("fx_rate"),
            ctx.arbitrage.get("landed_cost_lkr"),
            ctx.arbitrage.get("local_price_lkr"),
            ctx.arbitrage.get("margin_pct"),
            ctx.arbitrage.get("classification"),
        )
    elif phase_name == "phase3_defect_mining" and ctx.defects:
        await conn.execute(
            """
            INSERT INTO defect_dossiers
                (canonical_product_id, defects, source_count, generated_at)
            VALUES ($1, $2::jsonb, $3, now())
            ON CONFLICT (canonical_product_id)
            DO UPDATE SET defects = $2::jsonb, source_count = $3, generated_at = now()
            """,
            ctx.candidate_id, ctx.defects, len(ctx.defects),
        )
    elif phase_name == "phase4_merchant_forensics" and ctx.merchant_forensics:
        await conn.execute(
            """
            INSERT INTO merchant_forensics
                (merchant_id, physical_presence_verified, business_registry_age_days,
                 warranty_claims_verified, surcharge_map, dark_patterns_detected, audited_at)
            VALUES ($1, $2, $3, $4, $5::jsonb, $6::jsonb, now())
            ON CONFLICT (merchant_id)
            DO UPDATE SET physical_presence_verified = $2, business_registry_age_days = $3,
                          warranty_claims_verified = $4, surcharge_map = $5::jsonb,
                          dark_patterns_detected = $6::jsonb, audited_at = now()
            """,
            ctx.merchant_forensics.get("merchant_id"),
            ctx.merchant_forensics.get("physical_presence_verified"),
            ctx.merchant_forensics.get("registry_age_days"),
            ctx.merchant_forensics.get("warranty_verified"),
            ctx.merchant_forensics.get("surcharge_map", {}),
            ctx.merchant_forensics.get("dark_patterns", []),
        )
    # phase5 (peer cohort) typically writes to canonical_products.predecessor_id
    # and a lightweight peer-comparison JSONB field; omitted for brevity.


async def _commit_final_status(conn: asyncpg.Connection, ctx: PipelineContext):
    await conn.execute(
        """
        UPDATE canonical_products
        SET pipeline_status = $1, updated_at = now()
        WHERE id = $2
        """,
        ctx.status.value, ctx.candidate_id,
    )
    if ctx.errors:
        logger.info(f"Pipeline for {ctx.candidate_id} finished as {ctx.status.value} "
                    f"with {len(ctx.errors)} logged issues: {ctx.errors}")
```

**Key orchestration properties this satisfies:**
- Hard per-phase timeouts (`asyncio.wait_for`) so no single phase can consume another phase's budget — directly addresses Category E #82 and #94.
- Incremental DB commits per phase, so a mid-pipeline crash leaves a well-defined `pipeline_status` rather than corrupt/ambiguous partial data (#100, #87).
- LLM key pool with independent per-key cooldowns and an 80%-of-documented-limit safety margin, addressing #84 and #99.
- Schema validation on every LLM response regardless of which model (primary or fallback) produced it, addressing #85.

**Notes on these additions:**
- `merchant_forensics` and `defect_dossiers` are both "one current row per entity, upserted" tables (like the base blueprint's original `forensic_dossiers`) — they are not time-series and should stay unpartitioned; only `currency_arbitrage_logs` (and the original `price_history`) are genuinely time-series and partitioned accordingly.
- `component_teardowns` is append-only (a new row per distinct teardown source/finding) rather than upserted, since multiple teardowns of the same product over its lifecycle are all independently valuable evidence — don't collapse them into a single row.
- The `DATERANGE` + GiST index on `component_teardowns` lets you efficiently query "which teardown findings apply to units manufactured in this date range" when correlating a user's specific unit against known silent-revision defects.
