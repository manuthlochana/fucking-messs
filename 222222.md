## Part A: Architectural Hardening & Edge Case Matrix

Each rule below is written as a **failure mode → mitigation** pair so it can be dropped directly into your engineering backlog as a ticket.

### A1. Scraping & Data Ingestion Failures

1. **Honeypot links/fields.** Retail sites bury `display:none` or off-screen `<a>`/`<input>` elements to fingerprint bots. Never click or fill any element without first checking computed CSS (`visibility`, `opacity`, `width/height`, `position` off-viewport) via `page.evaluate`.
2. **Silent price-selector drift.** A CSS class rename (`.price-now` → `.prc-now`) breaks extraction without throwing an error — you just get `null` or a stale cached value. Run a **selector health-check job**: if a selector's yield rate drops below 90% of its 7-day rolling average, auto-quarantine the source and alert, rather than silently publishing `$0` or nulls.
3. **Disguised out-of-stock states.** Sites keep the "Add to Cart" button visible but disabled via JS, or swap price with "Contact Us" text while leaving old JSON-LD structured data cached. Cross-validate three independent stock signals (button `disabled` attribute, inventory count in inline JSON, and presence/absence of a stock-badge DOM node) — require 2-of-3 agreement before flipping status.
4. **Duplicate URL loops / infinite pagination.** Faceted search filters generate infinite unique query-string permutations (`?color=red&color=red&sort=asc...`). Canonicalize URLs before enqueueing: strip tracking params, sort remaining query params alphabetically, and dedupe against a Bloom filter before the URL ever enters the queue.
5. **Session/cookie fingerprint drift.** Reusing one browser context across thousands of requests produces a fingerprint that ages unnaturally (same TLS ClientHello, same canvas hash, static viewport) and gets silently shadow-banned (served fake/stale prices instead of blocked). Rotate context fingerprints (viewport, timezone, `navigator.hardwareConcurrency`, WebGL vendor strings) per N requests, not per session.
6. **JS-render race conditions.** SPA storefronts (Next.js/Nuxt) hydrate price after initial paint. `page.content()` grabbed too early returns skeleton loaders. Wait on a specific mutation observer signal (price node's `textContent` becoming non-empty and numeric-parseable) rather than a fixed `waitForTimeout`.
7. **Geo/IP-based content variance.** Some SL retailers serve different prices to LK vs. foreign IPs (installment pricing hidden from foreign IPs, or higher "export" pricing). Pin scraping proxies to Sri Lankan residential/mobile IP ranges, and periodically diff against a non-LK IP to detect and log geo-price discrimination as a data point, not an error.
8. **Cloudflare Turnstile / AWS WAF challenge loops.** Detect challenge pages by DOM fingerprint (specific iframe titles, `cf-turnstile` class) rather than HTTP status alone (many challenge pages return 200). On detection, back off that domain exponentially and route future attempts through a slower, higher-fidelity stealth profile rather than retrying immediately (retry storms get IP ranges blacklisted).
9. **Rate-limit cascades across shared proxy pools.** If Site A rate-limits your egress IP, a shared proxy pool means Site B (unrelated) may also start failing. Isolate proxy sessions **per target domain**, not per job, so one site's ban doesn't cross-contaminate others.
10. **JSON-LD / microdata poisoning.** Some sites embed stale or intentionally wrong `Product` schema (old MSRP) to game Google Shopping while showing a different live DOM price. Always prefer the rendered DOM price over structured data; use structured data only as a fallback or as a cross-check flag ("DOM price disagrees with schema.org price by >15%" → manual review queue).
11. **Currency/unit ambiguity in scraped text.** "Rs. 450,000" vs "450,000/-" vs "LKR 450000.00" vs a price shown pre-VAT vs post-VAT. Build a normalization layer with explicit regex + locale rules per source, unit-tested against a golden sample set per domain, re-run on every scraper deploy.
12. **Memory-leak-driven silent scraper death.** A Playwright context that never closes on an unhandled navigation error leaks tens of MB per run; on a 4GB VPS this OOM-kills the whole worker after a few hundred pages. Every scrape task must run inside a `try/finally` that force-closes context + browser, and the orchestrator should hard-recycle worker processes every N pages regardless of apparent health.
13. **Redirect-chain product mismatches.** A scraped URL 301s to a different (often newer/replacement) SKU during a product refresh cycle. Log the final resolved URL against the original; if they diverge, treat it as a **new candidate product** for entity resolution rather than silently overwriting the old listing's price history.
14. **A/B tested storefronts.** Some retailers run experiments where 50% of sessions see a different price/layout. A single scrape can't tell "real price change" from "which bucket I landed in." Take 2–3 samples per polling interval from different fingerprints before committing a price-change event.
15. **CAPTCHA-gated checkout-only fields.** Hidden checkout surcharges (installment fees, card fees) sometimes only render after adding to cart, which most scrapers don't simulate. Build a lightweight "synthetic cart" flow for a sampled subset of high-traffic SKUs weekly to capture true landed price, rather than assuming listing price = final price.

### A2. Canonical Entity & Variant Ambiguity

16. **Chipset/region SKU collapsing.** Exynos vs. Snapdragon variants of the same nominal model (common for Samsung in some regions) are *functionally different products* and must never share a canonical ID even if title strings match — key entity resolution on a **spec-fingerprint hash**, not just fuzzy title match.
17. **Storage/RAM combinatorics in free text.** "8/256", "8+256GB", "256GB (8GB RAM)", "256/8" — build a dedicated tokenizer state machine for storage-RAM pairs before falling back to generic Levenshtein distance, since generic fuzzy match will happily conflate 8/128 with 8/256.
18. **Color-name entropy.** "Desert Titanium" vs "Desert" vs "Natural Titanium" vs "Titanium Desert" — maintain a canonical color-alias table per product family; don't let color variance affect canonical *product* ID, only the *listing* variant ID (color should never fragment your master product graph, it should be a child attribute).
19. **Refurbished/open-box mislabeled as new.** Merchants routinely list grade-A refurb units under the "New" category to rank in default filters. Flag any listing with condition-signal keywords ("renewed", "open box", "grade A", "second owner", "as new") anywhere in title/description for mandatory condition-tag override, regardless of the category the merchant selected.
20. **Bundled accessory price inflation.** "iPhone 16 + free case + free screen protector" listings often carry a 5–10% markup that isn't disclosed as such. Detect bundle keywords and either (a) exclude bundled listings from headline price comparisons, or (b) attempt to estimate and subtract standard accessory value so bundle listings don't win "best price" purely by hiding markup in freebies.
21. **Carrier-locked vs. factory-unlocked ambiguity.** Especially relevant for grey-market imports; a carrier-locked unit is a different effective product for a local buyer. Require explicit lock-status extraction and treat unknown/unstated lock status as **incomplete data requiring manual flag**, never default to "unlocked."
22. **Regional keyboard/charger/plug variants.** A device imported for the Middle East market may ship with a different charger standard or lack Sri Lanka-specific bands (LTE band mismatches causing degraded connectivity). This is a genuine functional difference, not cosmetic — track "import region" as a first-class attribute affecting the risk score, not just metadata.
23. **Model-year vs. spec-refresh confusion.** Some brands release a "2024" and "2024 Pro" that share 90% of the title string but differ meaningfully (e.g., display panel supplier changed mid-cycle, known as "hardware revision"). Track SKU/model-number (not marketing name) as the ground-truth key wherever the retailer exposes it (barcode, EAN, MPN) and only fall back to fuzzy name matching when no hard identifier exists.
24. **Multi-language title collisions.** Sinhala transliterated titles ("අයිෆෝන් 16") need a transliteration-normalization pass before they can be compared via cosine similarity against Latin-script titles — don't run vector similarity on raw mixed-script text without a normalization step, or embedding quality degrades badly.
25. **Vector similarity false-merges on near-identical siblings.** "iPhone 16 Pro" and "iPhone 16 Pro Max" often score >0.95 cosine similarity on generic sentence embeddings because 90% of the title text is shared. Never merge purely on cosine similarity threshold — always require a secondary deterministic gate (exact storage/size/model-number match) before an auto-merge; anything below that gate goes to a human/LLM adjudication queue, not silent merge.
26. **Silent SKU discontinuation vs. temporary OOS.** A canonical product with zero live listings for 90+ days should be soft-archived (stop polling, keep historical data) rather than either deleted or kept in the active 1–6hr polling loop wasting compute.
27. **Duplicate canonical IDs from race conditions.** Two ingestion workers processing near-simultaneous new listings for the same real-world product can both fail to find a match and both create new canonical entries. Use a Postgres unique constraint on a normalized spec-fingerprint column (not application-level "check then insert") to make this a DB-level impossibility, or use `INSERT ... ON CONFLICT` with an advisory lock keyed on the fingerprint hash during resolution.
28. **Warranty-tier as a hidden variant.** "1 Year Agent Warranty" vs "6 Month Shop Warranty" vs "Checking Warranty" units are the *same physical product* but different *purchase products* from a risk standpoint — model warranty tier as a listing-level attribute that participates in ranking/filtering, never collapse it away during canonicalization.

### A3. Local Merchant Tactics & Deception

29. **Hidden installment surcharges (Koko/Mintpay/etc.).** Advertised price is often the cash price; selecting a BNPL/installment option at checkout silently adds 3–8%. Scrape the installment-plan API/DOM separately and always display **both** cash price and "true installment price" — never let a merchant's teaser price win a comparison against a competitor's honest all-in price.
30. **Credit-card surcharge stacking.** Some merchants add a card-processing fee only visible at the payment step. Same treatment as #29 — sample checkout flows periodically to capture true landed cost, tag listings where cash and card price diverge >2%.
31. **"Call for Price" as a bait tactic.** Used to dodge price-comparison bots specifically, often for genuinely competitive prices merchants don't want indexed publicly, or conversely to hide inflated prices until they've assessed the buyer. Flag these listings as "price unverified" rather than excluding them entirely, and where possible supplement with a lightweight WhatsApp-inquiry scraper/partner integration if the merchant offers one.
32. **Fake official-agent warranty claims.** Grey-market importers sometimes claim "1 Year Official Warranty" without being an authorized agent for that brand in Sri Lanka. Maintain a maintained allowlist of actual authorized agents per brand (sourced from brand's own regional distributor pages) and cross-check every "official warranty" claim against it — mismatches get downgraded to "unverified warranty claim" in the risk matrix, not taken at face value.
33. **Stock-count psychological pressure ("Only 2 left!").** Often fabricated/static regardless of actual inventory. Track whether the "X left" counter ever changes across polling cycles for a given SKU-merchant pair; if it's been static at the same low number for 30+ days, tag it as a manipulative-UX signal in the merchant reliability score.
34. **Fake discount anchoring (crossed-out "was" price never actually charged).** Compare the claimed "original price" against your own historical price-series for that listing; if you never observed that price in your own data and it's implausibly higher than market baseline, suppress the discount badge in your UI rather than propagating an unverifiable claim.
35. **Review-gating / incentivized reviews requiring proof-of-high-rating before code redemption.** Correlate suspiciously fast review velocity spikes immediately after purchase-confirmation emails with known incentivized-review patterns; downweight in the forensic layer (see A4).
36. **Bait-and-switch listing swaps post-purchase confirmation.** Harder to detect via scraping alone; supplement with a lightweight user-reporting flywheel ("this isn't what I received") feeding into merchant reliability score, since this is fundamentally a post-purchase fraud pattern outside pure price data.
37. **Undisclosed import/customs risk shifted to buyer.** Some listings are technically drop-shipped/pre-order imports where customs duty is the buyer's problem despite the listing reading like a local in-stock item. Detect via shipping-time language patterns ("7–14 working days", "pre-order") and surface as a distinct fulfillment-risk tag, separate from warranty risk.
38. **Currency-swing exploitation.** Merchants sometimes lag price updates *down* when LKR strengthens but update instantly *up* when LKR weakens. Track each merchant's historical price-update latency relative to CB exchange-rate movements in both directions — a persistent asymmetry becomes a quantifiable "pricing fairness" signal.
39. **Manufactured urgency via countdown timers with rolling/fake expiry.** If a "sale ends in" timer resets on page reload rather than being tied to a real backend deadline, flag the tactic in the merchant's dossier — this is detectable by scraping the same page twice a few minutes apart and diffing the timer's implied end time.
40. **VAT-inclusive vs VAT-exclusive price ambiguity.** B2B-leaning storefronts sometimes show VAT-exclusive as the headline price to look cheaper. Always normalize to VAT-inclusive consumer price for comparison purposes and store the raw + normalized values separately.

### A4. Forensic Review & Sentiment Contamination

41. **Astroturfed review-burst detection.** A sudden cluster of 5-star reviews within a short window, from accounts with low review-history depth and generic language patterns, is a classic astroturf signature. Score review authenticity using account-age, review-count-history, and language-diversity heuristics rather than star rating alone.
42. **Sponsored-influencer fluff contamination in YouTube transcripts.** Reviews that open with "Thanks to [Brand] for sponsoring this video" should have their entire transcript downweighted (not excluded — sponsored reviews can still contain real defect mentions buried mid-video, but the overall sentiment score should discount positivity bias). Extract disclosure phrases via regex/LLM classification pass before sentiment extraction.
43. **Localized batch defect vs. global hardware flaw conflation.** A specific defect reported heavily in one country/subreddit (e.g., a bad shipment batch that hit one region) shouldn't be presented as a universal hardware flaw. Tag defect mentions with source geography where inferable, and require corroboration across ≥2 independent geographic clusters before elevating a defect from "isolated reports" to "known hardware issue" severity in the forensic dossier.
44. **Recency-decay weighting for firmware-fixed issues.** Early-batch software bugs (e.g., a launch-week camera bug fixed in a subsequent OTA update) shouldn't permanently haunt a product's defect profile. Weight defect mentions by recency relative to release date and firmware-version context extracted from the review text where possible; explicitly annotate "reported at launch, since patched" vs. "persistent hardware issue."
45. **Competitor-brigading in Reddit/forum threads.** Coordinated negative-post campaigns from competing brand fan communities are a real phenomenon around major launches. Cross-reference defect claims against independent teardown sources (iFixit-style structural analysis, professional review outlets) before letting forum sentiment alone drive a "known issue" flag.
46. **Confusing normal user error with hardware defect.** E.g., "battery drains fast" complaints are often a settings/usage issue, not a hardware flaw, unless corroborated by teardown-level analysis (e.g., a known battery-cell supplier defect). Require the forensic layer to distinguish "commonly misused feature" from "verified hardware failure mode" as separate categories.
47. **Survivorship bias in only-negative-review scraping.** If your pipeline only pulls threads with complaint-keywords, you'll never see the (often much larger) satisfied-silent-majority baseline. Sample a control set of neutral/positive mentions proportionally, not just defect-keyword-matched threads, so the "defect rate" isn't artificially inflated by search bias.
48. **Translation-loss on Sinhala/Singlish forum sentiment.** Sarcasm and local idiom ("wassey" style expressions) can flip machine-translated sentiment polarity entirely. For local-language sources, use a two-pass approach: local-language sentiment classification first, then translate for the English-facing dossier — never translate-then-classify, which loses idiom-level nuance.
49. **Stale defect data outliving product relevance.** A defect thread from a product's launch year, if still ranked highly by an LLM's retrieval, can misrepresent a now-fixed product 2 years later. Enforce a hard recency ceiling in the RAG retrieval layer (e.g., exclude/heavily discount forum sources older than 18 months unless the topic is explicitly "long-term reliability").
50. **Overweighting XDA/enthusiast-forum severity relative to mainstream buyer risk.** XDA users report edge-case bootloader/rooting issues irrelevant to 95% of buyers; the forensic layer should tag defect severity by "affects stock/normal-use configuration" vs. "affects modified/enthusiast configuration only" so the AI advisor doesn't scare a normal buyer with an enthusiast-only failure mode.

### A5. System Resource & API Limiting on Low-Spec VPS (2-Core / 4GB)

51. **Playwright memory leak prevention.** Never reuse a `BrowserContext` across unrelated jobs; close contexts explicitly, and set a hard process-level memory ceiling (e.g., `--max-old-space-size` equivalent via a supervisor) that force-kills and respawns a worker if it exceeds ~600–800MB resident, since Chromium contexts are the single biggest leak vector on constrained VPS.
52. **Concurrency ceiling tied to actual RAM headroom, not CPU count.** With 4GB total and the OS/DB/queue consuming a baseline ~1GB, cap concurrent headless browser instances at 2–3 max regardless of the 2 cores, since each Chromium instance can spike to 300–500MB under heavy JS pages.
53. **Prefer HTTP-only scraping wherever a site doesn't require JS rendering.** Reserve Playwright for genuinely JS-dependent storefronts; a lightweight `httpx`/`curl`-based fetch + HTML parse is an order of magnitude cheaper in both memory and CPU — maintain a per-domain flag for "needs-browser" vs. "static-fetch-ok" determined empirically, and re-test periodically since sites migrate to SPA frameworks over time.
54. **Queue backpressure instead of unbounded task acceptance.** An async queue (Redis/RQ, or even a simple Postgres-backed queue) must reject/delay new enqueue requests once in-flight worker memory approaches the ceiling, rather than accepting unbounded work and letting the OOM killer choose victims — you want graceful degradation (delayed freshness) over a total crash.
55. **Graceful degradation during 429 cascades across the multi-LLM free-tier pool.** When Gemini free-tier hits its RPM cap, don't hard-fail the pipeline — implement a priority queue where high-value tasks (new-product forensic analysis) get first claim on remaining quota, while low-value tasks (routine re-summarization) get deferred to off-peak hours or a lower-tier model.
56. **Exponential backoff with jitter, tracked per-API-key.** With key rotation across multiple free-tier accounts, a naive round-robin retry can hammer all keys simultaneously right after a shared trigger event (e.g., a burst of new products). Track rate-limit state per key independently and route around whichever keys are currently cooling down.
57. **Batching LLM calls instead of per-listing calls.** For the 15-minute forensic pipeline, batch multiple review snippets into a single prompt (within context-window limits) rather than issuing one API call per review — this is both cheaper on your free-tier quota and reduces total wall-clock time under CPU constraints (fewer concurrent HTTP connections to manage).
58. **Disk I/O as a silent bottleneck.** Constant Playwright screenshot/trace logging (useful for debugging) can fill disk and cause I/O wait spikes on a shared/low-spec VPS; disable tracing in production by default and only enable it selectively for a domain under active debugging.
59. **Database connection pool sizing matched to worker count.** On a 2-core VPS running Postgres locally alongside your app, an oversized connection pool (e.g., default 100) causes context-switching thrash; size the pool to roughly `(2 × cores) + effective_spindle_count` as a starting heuristic and tune from there, keeping total Postgres `max_connections` conservative.
60. **Scheduled maintenance windows for VACUUM/ANALYZE.** High-frequency price-delta writes (every 1–6hrs across many SKUs) bloat tables fast; schedule autovacuum tuning (lower `autovacuum_vacuum_scale_factor` for the price_history table specifically) rather than relying on Postgres defaults tuned for larger hardware.
61. **Circuit-breaker per scraping domain.** If a domain fails N consecutive times, stop hammering it for a cooldown period rather than retrying every cycle — this both respects the target site (reduces your ban risk) and frees your limited concurrency slots for domains that are actually working.
62. **Swap as a last-resort safety net, not a performance strategy.** Configure a modest swap file (1–2GB) purely to convert an otherwise-instant OOM kill into a graceful (if slow) degradation window your monitoring can catch — but alert loudly on any sustained swap usage, since relying on swap as steady-state behavior on a 4GB box will make everything crawl.

```
relative to true global value, (2) buying into a warranty trap that will cost

only after the return window closes. Every response should visibly move the
user closer to avoiding at least one of these.
```

## Part C: PostgreSQL + pgvector Schema Optimization

### C1. Design principles for low-spec hardware at scale

- **Partition the time-series table** (`price_history`) by month; on a 2-core/4GB box, an unpartitioned table with millions of rows makes both `VACUUM` and index maintenance prohibitively slow. Partitioning keeps working-set size (and therefore index size in memory) small per query.
- **Keep `pgvector` embeddings out of the hot write path table.** Store them in a dedicated `product_embeddings` table so high-frequency price writes never touch a large-vector-column table (vector columns bloat WAL significantly on update).
- **Use `HNSW` index (pgvector ≥0.5) over `IVFFlat`** for this scale (low-millions of vectors) — HNSW gives better recall/latency tradeoff and doesn't require periodic re-clustering the way IVFFlat does, which matters when you don't have spare CPU for maintenance jobs.
- **JSONB for genuinely variable attributes only** (spec sheets differ wildly across categories — phones vs. laptops vs. appliances); keep anything you filter/sort on frequently (price, warranty_tier, in_stock) as real typed columns with B-tree indexes, not buried in JSONB.

### C2. Core DDL

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- for fast fuzzy title matching

-- Canonical product graph
CREATE TABLE canonical_products (
    id              BIGSERIAL PRIMARY KEY,
    category        TEXT NOT NULL,
    canonical_name  TEXT NOT NULL,
    model_number    TEXT,                 -- brand's true SKU/MPN when known
    spec_fingerprint TEXT NOT NULL,        -- deterministic hash of normalized core specs
    attributes      JSONB NOT NULL DEFAULT '{}',  -- variable per-category spec sheet
    us_msrp_usd     NUMERIC(10,2),
    msrp_source     TEXT,
    msrp_as_of      DATE,
    predecessor_id  BIGINT REFERENCES canonical_products(id),
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (spec_fingerprint)
);

CREATE INDEX idx_canonical_category ON canonical_products (category) WHERE is_active;
CREATE INDEX idx_canonical_name_trgm ON canonical_products USING gin (canonical_name gin_trgm_ops);
CREATE INDEX idx_canonical_attrs ON canonical_products USING gin (attributes jsonb_path_ops);

-- Embeddings kept separate from hot-write tables
CREATE TABLE product_embeddings (
    canonical_product_id BIGINT PRIMARY KEY REFERENCES canonical_products(id) ON DELETE CASCADE,
    embedding       vector(384),           -- match your chosen embedding model's dim
    model_version   TEXT NOT NULL,
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_product_embedding_hnsw
    ON product_embeddings USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Merchant registry (for reliability scoring)
CREATE TABLE merchants (
    id              BIGSERIAL PRIMARY KEY,
    name            TEXT NOT NULL UNIQUE,
    domain          TEXT NOT NULL,
    reliability_score NUMERIC(3,2) DEFAULT 0.50,
    is_authorized_agent_for JSONB DEFAULT '[]',  -- list of brand names it's verified for
    known_surcharges JSONB DEFAULT '{}',          -- e.g. {"card": 0.02, "koko": 0.05}
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Live listings (one row per merchant×canonical product, mutable)
CREATE TABLE listings (
    id                  BIGSERIAL PRIMARY KEY,
    canonical_product_id BIGINT NOT NULL REFERENCES canonical_products(id),
    merchant_id         BIGINT NOT NULL REFERENCES merchants(id),
    source_url          TEXT NOT NULL,
    raw_title           TEXT NOT NULL,
    current_price_lkr   NUMERIC(12,2),
    warranty_tier       TEXT CHECK (warranty_tier IN
                          ('official_agent','shop_inhouse','checking','unstated')),
    warranty_verified   BOOLEAN NOT NULL DEFAULT FALSE,
    condition           TEXT CHECK (condition IN ('new','open_box','refurbished','used')),
    in_stock            BOOLEAN,
    stock_confidence    SMALLINT,           -- 0-3, how many independent signals agreed

    selector_health_ok  BOOLEAN NOT NULL DEFAULT TRUE,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),

CREATE INDEX idx_listings_merchant ON listings (merchant_id);
CREATE INDEX idx_listings_price ON listings (canonical_product_id, current_price_lkr)
```

### C3. Maintenance & scaling notes for this hardware tier

- **Autovacuum tuning for `price_history`:** set a table-specific override —
  `ALTER TABLE price_history SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_analyze_scale_factor = 0.01);`
  — since default 20% scale factor means vacuum almost never triggers on a fast-growing table until it's already bloated.
- **Partition pruning is your main defense against slow queries at scale.** Always query `price_history` with an explicit `recorded_at` range so the planner can prune to 1–2 partitions instead of scanning the whole time series.
- **Drop/detach partitions older than your retention policy** (e.g., 24 months) rather than deleting rows — `DETACH PARTITION` + archive-to-cold-storage is near-instant versus a row-by-row `DELETE`, which would be brutal on this hardware.
- **HNSW build is memory-hungry at insert time** — for the initial bulk-load of embeddings, build the index *after* loading all vectors rather than incrementally, and consider running that one-time build during an off-peak maintenance window given the 4GB ceiling.
- **`work_mem` should stay conservative** (e.g., 16–32MB) given the low RAM ceiling and multiple concurrent connections; rely on the HNSW/GIN indexes to avoid large in-memory sorts rather than raising `work_mem` globally.
